# byteworker · 知识库回答引用协议

> 由 `SKILL.md`「知识库检索回答引用」路由到这里。凡用户可见回答中的事实来自
> `knowledge/`、`raw_data/`、`reports/`、`journal/` 或 `dashboard.md` 派生内容,都必须执行本协议。

## 1. 目标与范围

引用要让使用者能判断三件事:

1. **这句话来自哪里**:具体到原始飞书文档、妙记 / 录屏、会议、群聊窗口、网页或本地文件;
2. **byteworker 何时收录**:使用 raw frontmatter 的 `ingested`,不得拿节点 `created` /
   `updated` / `last_verified` 或 raw 文件名冒充;
3. **证据是否仍新鲜**:同时展示原文日期 / 会议时间 / `digest_period` / `source_window`
   中能确认的时间;没有就明确写“原文时间未记录”。

适用场景包括 `search`、`brief`、`dashboard` 中从节点拉取的状态、日报 / 周报生成与回显、
已归档报告的再查询,以及任何没有显式子命令但实际检索了知识库的回答。纯闲聊或完全不使用
知识库的回答不强加引用。

## 2. 先建立“结论 → 原始来源”映射

写答案时同步记录每条事实性结论实际使用了哪些节点 / raw / 报告,不要先写完整答案再随手挑几个
看似相关的来源:

1. 从命中节点的 `sources` 出发。值是 `raw_id` 时,必须定位对应 `raw_data/*.md` 并读取
   frontmatter;值是 URL 时,保留 URL,但继续查是否有同 URL / `source_uid` 的 raw。
2. 从 `links` 遍历得到的事实也使用**承载该事实的节点自身 `sources`**,不能只引用起点节点。
3. `reports/` 是二手汇总。通过报告的「来源索引」继续追到节点 / raw,最终优先引用原始 raw;
   可把报告路径作为“经由”补充,但不能用日报 / 周报替代可找到的原始文档或录屏。
4. `journal/` 主要是操作日志,不是业务事实证据。由 journal 找到对应 raw / 节点后再引用;
   找不到原始证据时,不得仅凭 journal 写成高置信事实。
5. 一条结论由多个来源共同支持时全部标注;一个来源支持多条相邻结论时可以复用同一编号。

## 3. raw 元数据解析

每个被引用的 raw 至少读取并展示:

- **来源名称**:`source_title`;群聊使用 `source_chat_name`;历史条目可回退到明确的 `title`
  或 raw 正文标题,但标“历史字段 / 由归档标题识别”;
- **来源类型**:
  - `feishu_doc` → 飞书文档;
  - `feishu_minutes` → 飞书妙记 / 录屏;
  - `feishu_meeting` → 飞书会议;
  - `feishu_chat` → 飞书群聊窗口;
  - `web` → 网页 / 论文 / wiki;
  - `local_md` → 本地文件;
- **原始出处**:`source_url`;历史妙记可回退到明确的 `recording_url`;本地文件用绝对路径;群聊无 URL 时给
  `source_chat_name + source_chat_id + source_window`,并明确“无可打开的原始链接”;
- **收录时间**:`ingested`,面向用户显示为 `YYYY-MM-DD HH:MM` 并保留时区语义;
- **原文时间 / 覆盖范围**:优先使用明确的发布日期、会议时间、`digest_period`、
  `source_window`,或语义明确的历史字段 `event_time` / `source_created_at`;不得根据收录时间
  反推原文发生时间;
- **版本**:有 `source_revision` 时展示;历史条目可回退到 `revision_id`;必要时展示 `raw_id`
  供库内核对。

历史 raw 的兼容规则:

- 有 `fetched_at` 但无 `ingested` → 写“抓取时间(历史字段):…”;
- 只有 `digest_date` → 写“收录日期(历史字段,具体时刻未记录):…”;
- 两者都没有 → 写“收录时间未记录”,不得从文件名、节点创建时间或 git 时间猜测;
- 没有 `source_url` / `recording_url` → 写“原始链接未记录”,保留可确认的标题、来源类型和
  `raw_id`;
- 节点只有直接 URL、找不到对应 raw → 可引用该 URL,但必须写“未找到 raw 归档,
  收录时间未记录”;
- 关键结论的原始出处或收录时间缺失时,整体置信度最高为“中”,并指出缺口。

## 4. 用户可见格式

事实性句子或条目后紧跟论文式编号,不要只在答案末尾堆一批无法对应结论的来源:

```markdown
项目已经进入灰度阶段,但线上覆盖率尚未在库中得到验证。[S1]

## 引用

- [S1] 《项目周会》— 飞书文档；原始出处:[打开原文](https://...);
  原文时间 / 覆盖:2026-W30;收录时间:2026-07-27 10:32(Asia/Shanghai);
  版本:revision 18;库内归档:`raw-2026-07-27-project-weekly`.

置信度:中 —— 阶段状态有直接文档支持,线上覆盖率没有可核验证据。
```

规则:

- 每个包含知识库事实的段落 / 列表项至少有一个能覆盖该事实的 `[S<n>]`;纯建议明确标“建议”,
  不伪造引用。
- 「引用」放在答案末尾、「置信度」之前;短答案也不能省略原始出处与收录时间。
- 同一原始来源只编号一次;按正文首次出现顺序编号。
- 不展示与答案无关的全量 `sources`;只列实际支持回答的证据。
- 不把 `raw_id`、节点 id 或报告路径单独当作“原始出处”;它们只能作为库内核对信息。
- URL / 标题 / 时间缺失时照实输出缺失状态,不得补写看似合理的值。

## 5. IM 报告与非 digest 来源

`reports/im/` 中尚未提升为标准 digest 的 thread 没有 raw 原文。引用时使用单独编号并写:
群 / 会话名、`chat_id`、消息时间或窗口、`message_ids`(若有)、报告 `generated_at` / 扫描时间,
以及“尚未形成标准 digest raw,无法提供原始录屏 / 文档链接”。这类证据不得标为高置信。

`context.md`、`todo.md`、用户本轮直接输入不是 digest 来源。若回答同时使用这些信息,单列
“用户确认 / 本地状态”,不要伪装成 `[S<n>]` 原始文档引用;有记录日期就展示,无日期就写未记录。

## 6. 新鲜度与置信度

引用时间与置信度必须同时出现,但含义不同:

- `ingested` 只表示 byteworker 何时把该版本收进库,**不等于事实发生时间或仍然有效**;
- `last_verified` 表示节点最后被新输入 / 人工确认的日期,也不能替代原始出处;
- 对排期、指标、组织关系、项目状态、当前负责人等易变化事实,若原文时间 / 覆盖范围明显旧,
  在正文直接提示“可能已过期”,不要等用户自己算;
- 新旧来源冲突时并列引用并说明冲突,不得只引用较新一份后静默覆盖历史。
