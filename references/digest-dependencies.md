# byteworker · digest 细则 —— 重要依赖发现与范围确认

> 由 `SKILL.md`「digest」一节路由到这里。执行任何 digest 前必读。本文件只决定是否扩大
> 本次摄取范围;不改变「默认只处理用户当前指定对象」的原则。

## 什么算重要依赖

当前对象引用的历史会议、其它文档、附件、嵌入表格 / 多维表格、前置方案、决策记录或数据源,
满足下面任一项才算重要依赖:

- 当前对象把关键结论、决策、指标口径、风险判断或行动项的**唯一依据 / 完整定义**放在该来源中;
- 当前对象明确表示「沿用 / 取代 / 变更 / 依赖」该来源,不读它就无法判断新旧关系或冲突;
- 该来源承载当前对象缺失的关键会议讨论、反对意见、约束、数据表或实验结果,缺失会让 digest
  对项目状态、决策因果或参与方立场产生实质误读;
- `context.md` 重点关注的项目 / 人 / 指令在当前对象里只被简写,而该来源显然承载完整内容。

以下通常**不算**重要依赖:普通背景链接、延伸阅读、同主题资料列表、仅用于致谢 / 举例的引用、
当前正文已经自足复述的证据、与本次要沉淀的结论无关的导航链接。不要看到链接就询问用户。

## 发现与去重

1. 只扫描当前已获授权对象中的显式线索:URL、`<cite type=doc>`、附件 / embed token、具名历史会议、
   「详见 / 延续 / 基于 / 数据见 / 决议见」等引用。可以读取标题、类型、日期等轻量元数据来消歧,
   **不得在用户同意前读取依赖正文或把它写入 raw / 节点**。
2. 先查 INDEX、相关节点和 `raw_data/` 的 `source_uid` / `source_url` / `source_revision`:
   - 已有足够新且已 digest 的版本 → 复用现有节点作为上下文,不再询问重复摄取;
   - 已有版本明显过旧或当前对象明确指向新版本 → 仍作为候选,说明「KB 中已有旧版」;
   - 无法唯一定位 → 只报名称 / 线索并请用户补链接,不猜 URL。
3. 同一候选被多处引用时合并;优先保留最直接、对当前结论影响最大的依赖。默认只判断**一跳**。
   已获同意的依赖又暴露二跳引用时不得自动铺开;仅当二跳同样满足上面的重要门槛,再单独询问。

## 询问方式

没有重要依赖时静默继续,不要为了证明扫描过而打断用户。有重要依赖时,在读取依赖正文和写知识
节点前**合并成一次短询问**,每项包含:

- 依赖名称 / 类型 / 链接(若已知);
- 为什么它会影响当前 digest(对应哪条结论、决策、数据或风险);
- 建议:「加入本次」或「可暂缓」。

示例:

> 我发现 2 个可能影响本次消化完整性的依赖:①《Q3 资源决议》—— 当前排期直接沿用其中的资源
> 上限,建议加入;② 6 月 18 日评审会—— 当前文档没有记录被否决方案及原因,建议加入。要把哪几个
> 一并 digest?也可以回复「都不加」,我会只处理当前文档并标注待核实边界。

用户的选择只授权本次明确选中的对象:

- **同意** → 把选中对象加入本次范围,分别执行来源读取、幂等检查和 raw 留存,再用全部已确认
  内容做冲突检测与节点扇出;汇报中列出扩展来源。
- **拒绝 / 暂缓 / 未提供链接** → 继续 digest 当前对象;不得补写依赖中的事实。受影响内容标注
  「依赖未摄取 / 待核实」,汇报中说明缺口与可能影响。
- **只选部分** → 仅摄取选中的依赖;其余按暂缓处理。

## 与会议簇、规模预估的关系

- 同一场会的日历、妙记、投屏文档是会议簇组成物件,按 `references/digest-meeting.md` 一次确认;
  组成物件内部引用的历史会议 / 其它资料才走本规则。
- 扩展后若成为大型输入,先把「依赖范围确认」和「摄取深度确认」合并成一次用户交互,再按
  `references/digest-large.md` 处理;不要先问一轮依赖、马上又问一轮规模。
