# Byteworker 全项目技术架构审查

2026-11-27，审查基线 `c25abff`。建议保留本地 Markdown + Git、统一 CLI、来源适配器，以及 Agent 做语义判断、代码核验写入的分工。**需要局部重构。第一优先级是统一 Digest 的提交判定、拆开日报归档和投递的完成条件、消除 Viewer 设置对运行中授权的意外影响。** 这三处均已用临时合成库复现。全库重写或先建设通用调度平台，收益尚无证据。

## 已复现的正确性问题

### P1 · 未提交的 raw 会让摄取重试跳过缺失的知识节点

单源事务先把标为 `digested` 的 raw 写入工作树，随后才写出处、节点、索引和 Git 提交。重试时，预检只看工作树 raw 的内容键与状态。标准 flow 在预检返回 `noop` 后把自己标为终态。普通异常可以触发回滚，进程终止会留下另一条恢复路径。[预检](../../../../lib/digest_txn.py#L419) · [写入次序](../../../../lib/digest_txn.py#L1872) · [flow 终态](../../../../lib/digest_flow.py#L431)

两次独立实验使用仓库自带的合成 fixture。在 raw 第一次替换成功后结束子进程。v1 再执行同一 plan 返回 `noop`，Git 仍只有初始化提交，目标节点不存在。v2 从新的本地 Markdown flow 重新 prepare，得到 `phase=noop, next_action=none`，而库内零知识节点，Git 尚无 HEAD。这也可能发生在其他读取者观察尚未完成的写入时，后者属于并发风险推断。

另一次实验让 Git commit 真正成功，只给随后的 `rev-parse HEAD` 注入读取异常。调用报错并恢复工作树和索引，但 HEAD 已前移。复核时新提交包含 raw，工作树没有 raw，索引相对 HEAD 有五个差异。单源和批量 Digest 共享这一异常处理形态，非 Digest mutation 已单独处理 HEAD 恢复。本次对提交后异常的注入覆盖了单源。[单源提交](../../../../lib/digest_txn.py#L1924) · [批量提交](../../../../lib/digest_txn.py#L2079) · [mutation 回滚](../../../../lib/kb_mutation.py#L695)

**重构边界**：把重复摄取判定绑定到可核对的已提交版本。发现相同但未经提交的 raw 时，返回明确的恢复状态，保护原有用户编辑。提交前失败按现场回滚，提交成功但回执丢失时优先从 Git 对账。单源和批量复用这个边界，保留各自的业务校验。验收覆盖提交前终止、提交后回执读取失败，以及已完成的旧格式来源仍然幂等。

### P1 · 基础日报会消耗正式日报和可选投递所需的待办

正常 tick 先运行独立 Markdown 发布，再领取调度任务。基础版写完就从 `pending_periods` 移除该期。调度器跳过已有归档的周期，待办为空时不再返回日报候选。HTML 和配置过的飞书摘要则由另一条 `report complete` 路径产生。基础版按期落盘具有明确价值，两种产物共用“本期完成”才产生冲突。[tick](../../../../lib/dreaming_diagnostics.py#L22) · [移除待办](../../../../lib/dreaming_daily.py#L243) · [领取条件](../../../../lib/dreaming_scheduler.py#L1222) · [投递入口](../../../../lib/dreaming_report_completion.py#L68)

使用两个初始设置相同的临时库，在同一工作日 20:30 开启日报管理和摘要投递。直接运行 `run_due` 领取到 `daily`。另一库先 `publish_due_daily` 再 `run_due`，得到 Markdown 和 `process` 租约，日报待办为空，没有 HTML 或投递条目。未调用真实飞书。独立入口只发本地 Markdown 符合其文档，但现有自动路径没有给已配置的后续工作留下任务。[独立发布与正式报告契约](../../../../references/dreaming-reports.md#到点独立发布)

**重构边界**：沿用同一报告类型和周期，分别记录基础版已发布、详细报告已生成、摘要待投递或已送达。消费其中一项只完成对应工作。用真实 tick 次序验证重复唤醒、长摄取占租约、已启用和已关闭投递四种情况，重复执行应保持一份有效版本和一条对应投递记录。

### P1 · Viewer 保存无关偏好，会使正在处理的消息授权失效

Dreaming 设置页编辑一个字段时会收集整页，包括当前 IM 授权。设置服务见到 `im` 就调用授权 writer。writer 每次都递增授权版本，进行中的后台批次提交必须匹配该版本。前端保存队列能保护同一页面的编辑顺序，无法消除这一服务端副作用。[表单收集](../../../../viewer/index.html#L3370) · [设置写入](../../../../lib/settings.py#L565) · [授权版本](../../../../lib/dreaming_grants.py#L98) · [批次提交](../../../../lib/dreaming_batch.py#L337)

在合成库中开通 monitored，创建一个已完成分析、等待提交的消息批次。按页面生成的字段组合保存日志保留天数，同时原样传回 IM 模式和持久化选项。授权版本从 1 变为 2，原批次提交返回 `DREAMING_GRANT_STALE`。本实验经过实际设置服务和批次 writer，页面字段组合由前端代码核对。

**重构边界**：前端只发送实际修改的字段，服务端对等值授权保持幂等。真正缩小范围仍须作废旧授权并执行清理。用同一个未提交批次验证两种结果，可同时防止修复损害撤权保护。

## 测试和治理的维护成本

98 个测试模块、27,961 行，791 项测试。macOS、Python 3.13.16、Node 22、coverage.py 7.17.5。全套无覆盖统计用时 107.601 秒，开启子进程和分支覆盖后用时 152.312 秒，两轮全部通过。综合覆盖率 78.7%，门槛 75%。这是 unittest 报告的执行时间，不含依赖安装与覆盖数据合并。开启覆盖时最慢单例约 4.4 秒。本机测量支持继续保留 CI 全量门禁，日常编辑适合先跑受影响模块。

**主要负担是改动脆弱性和漏测的位置。** Viewer 布局测试要求源码保留一条特定 CSS 注释、精确像素、函数名及字符串；部分 Node 运行测试按相邻函数名截取 HTML 才执行。改注释、移动函数或提取模块都会破坏测试，界面行为可以完全相同。CLI 边界测试规定 Dreaming 至少六个文件，也会阻碍有意合并。与此同时，已有 Digest 回滚用例覆盖 pre-commit 拒绝，漏掉本次复现的原始文件落盘后进程消失和提交成功后读取回执失败。[布局断言](../../../../tests/test_viewer_layout_contract.py#L56) · [源码切片](../../../../tests/test_viewer_save_queue.py#L14) · [文件数断言](../../../../tests/test_command_refactor_boundaries.py#L26) · [既有故障测试](../../../../tests/test_digest_txn.py#L1177)

保留真实 Git、跨进程锁、来源兼容、引用、Viewer 访问控制及少量完整 CLI 测试。UI 逻辑先从 4,887 行的 HTML 中提取能独立加载的模块，用实际输入和输出验证导航及保存结果。下一次改变提示词时，用行为样例替换对非必要原句的断言。把重复造库和数据构造从冗长用例中提取出来，例如会议双来源提交的一项测试有 221 行。将新增测试集中在上述可失败的交接点，无需为每个新 wrapper 再加一套契约。[Viewer 运行用例](../../../../tests/test_viewer_runtime.py#L50) · [会议批量用例](../../../../tests/test_digest_txn.py#L854)

## 重构顺序与验收

1. **先处理三个 P1。** 每个问题各用一个独立变更，先固定可复现的失败场景。验收分别看 Git 与工作树是否一致、同一期配置的产物是否完成、无关设置能否让原批次照常提交。
2. **然后减少 Agent 必须记住的流程。** 先改搜索和维护路由，再收回后台确定性接续。按改前改后的任务结果、规则体积和调用次数判断效果，保留授权、引用、写入回执与无人值守静默约束。
3. **随后沿真实改动拆模块和测试。** 优先隔离 Dreaming 的来源收尾和报告调度，Viewer 按保存与渲染边界拆；来源适配器随下次来源改动迁移。若逐来源工作、恢复与重放仍难以在现有状态层保证，再评估已有 SQLite 协调器方案及迁移成本。

本次为源码、提交历史、测试和合成故障审查。执行了架构契约、全量测试、覆盖率、Python 编译和 shell 语法检查。未使用真实业务知识库、真实 provider、模型或宿主唤醒进行端到端验收。报告仅登记本次证据，产品架构、持久化格式与兼容层均无改动。
